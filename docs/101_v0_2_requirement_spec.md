# 《叙事校准程序 / 末班车站》v0.2 需求规格

## 1. 版本定位

v0.1 已完成低保真功能闭环：

```text
三问校准
→ 末班车站
→ 三轮主线选择
→ 四个调查物
→ 三个结局
→ 重新开始
```

v0.2 的目标不是扩展剧情长度，也不是做完整商业 Demo，而是在不增加主线轮次和结局数量的前提下，把 v0.1 打磨成一个可以给外部玩家试玩、并具备明确记忆点的增强版原型。

v0.2 的核心目标是：

```text
让玩家不迷路；
让车站空间更明显地记录并反馈玩家选择；
让低保真 UI、动效、音效共同强化"系统正在生成并观察玩家"的感觉；
让系统出现一次可感知的 AI 式介入。
```

## 2. v0.2 一句话目标

在保留 v0.1 主线结构的基础上，将《叙事校准程序 / 末班车站》打磨成一个 5–8 分钟的可外部试玩版本，使玩家明显感到：

```text
车站不是普通背景；
它正在被系统生成；
它记录了玩家选择；
它会根据玩家行为改变反馈；
它甚至会在某一刻改写玩家的行动选项。
```

## 3. v0.2 总原则

### 3.1 补短板 / 养长板原则

每个需求都必须先判断：

```text
它是在补短板，还是在养长板？
如果是补短板，是否只需补到可玩即可？
如果是养长板，是否强化"系统记录、解释并反馈玩家选择"？
它是否能为后续扩展复用？
它是否会导致未来反复推翻重做？
```

补短板需求只做到：

```text
不阻碍玩家理解；
不阻碍玩家推进；
不阻碍外部试玩反馈。
```

养长板需求必须强化：

```text
系统记录玩家选择；
系统解释玩家选择；
车站空间反馈玩家选择；
AI / 系统介入玩家行动界面。
```

### 3.2 范围冻结原则

v0.2 不做：

```text
第四轮主线；
第四结局；
自由输入；
多 NPC；
复杂地图探索；
背包 / 道具系统；
完整动态音乐系统；
AI 全流程生成剧情；
真实 AI 决定结局；
复杂写实美术；
复杂 Shader；
联网发布版本。
```

v0.2 可以做：

```text
操作引导；
设备反馈；
低保真 UI；
几何车站背景；
刷新动效；
最小音效；
Mock AI 动态引导；
受限选项改写；
可选 API 实验开关。
```

## 4. v0.2 核心需求

v0.2 包含 6 个核心需求：

```text
需求 1：系统待处理项与主交互高亮
需求 2：车站空间反馈增强
需求 3：系统生成式入场与低保真几何车站背景
需求 4：低保真设备按钮视觉化
需求 5：系统锚点音效与低频环境音
需求 6：AI 动态引导与受限选项改写
```

推荐实施顺序：

```text
第一批：试玩可理解性
1. 系统待处理项与主交互高亮
2. 低保真设备按钮视觉化
3. 车站空间反馈增强

第二批：完成度与记忆点
4. 系统生成式入场与低保真几何背景
5. 公告屏 / 文本刷新动效
6. 系统锚点音效与低频环境音

第三批：AI 原生雏形
7. Mock AI 动态引导
8. 受限选项改写
9. 可选 API 实验开关
```

如果时间不足，真实 API 可以延后；但 Mock AI 的"动态引导 + 受限选项改写"建议保留，因为这是 v0.2 最可能制造惊艳感的部分。

# 5. 需求 1：系统待处理项与主交互高亮

## 5.1 目标

让陌生玩家始终知道下一步该做什么，同时保持冷淡系统 UI 氛围。

解决的问题：

```text
玩家不知道该点哪里；
玩家不知道公告屏是否是推进主线的入口；
玩家不知道第三轮后如何进入最终判断；
玩家可能把调查物当成纯装饰。
```

## 5.2 实现要求

新增一个系统提示文本区域，建议命名为：

```text
ObjectiveLabel
```

显示风格：

```text
系统待处理项：读取电子公告屏
系统待处理项：选择一项行为
系统待处理项：继续记录
系统待处理项：查看最终判断
系统待处理项：记录完成
```

不要写成教程腔：

```text
请点击电子公告屏继续游戏。
```

当前主交互对象应有轻微高亮：

```text
需要点击公告屏时：公告屏按钮高亮；
需要选择 A/B/C/D 时：选项区高亮；
需要查看最终判断时："查看最终判断"按钮高亮；
支线调查物始终可点，但不强制高亮。
```

## 5.3 不做内容

```text
不做新手教程弹窗；
不做大段操作说明；
不强迫玩家点击全部调查物；
不改变主线结构；
不改变结局判断。
```

## 5.4 验收标准

```text
玩家进入车站后知道应该先看公告屏；
公告屏调查后知道应该选择 A/B/C/D；
每轮选择后知道是否需要继续或查看公告屏；
第三轮后知道如何进入最终判断；
提示符合冷淡系统 UI 风格；
没有破坏原有主线流程。
```

# 6. 需求 2：车站空间反馈增强

## 6.1 目标

让玩家感觉车站不是背景，而是在根据玩家选择倾向逐步改变。

v0.1 的反馈主要集中在文本框中。v0.2 需要让公告屏、时钟、广播灯、出口门更明显地承担"系统记录玩家"的功能。

## 6.2 关键概念：dominant_trait

新增概念：

```text
dominant_trait
```

可能值：

```text
doubt
control
obedience
mixed
```

计算规则第一版可以很简单：

```text
如果 doubt 最大 → doubt
如果 control 最大 → control
如果 obedience 最大 → obedience
如果三者平局或接近 → mixed
```

`anomaly` 不作为主倾向。它表示叙事噪声 / 系统失真值。

## 6.3 anomaly 定义

```text
anomaly：叙事噪声 / 系统失真值。
它记录玩家行为导致车站生成过程偏离稳定流程的程度。
它不直接决定顺从、怀疑、控制三类结局。
它影响文本语气、设备失真、刷新强度、音效失真和最终摘要中的"叙事噪声"。
```

不要新增 anomaly 结局。

## 6.4 每轮一个主反馈物件

为避免信息过载，v0.2 遵守：

```text
每轮都有变化；
但每轮只突出一个主反馈物件；
其他物件只做轻微辅助。
```

建议分配：

```text
第一轮：电子公告屏主反馈
第二轮：广播灯主反馈
第三轮：出口门主反馈
时钟：贯穿辅助反馈，表现 anomaly / 时间异常
```

## 6.5 反馈方向

第一轮公告屏主反馈：

```text
doubt：
解释请求已登记。
上一行为：询问广播。

control：
目的地字段被访问。
上一行为：查看出口。

obedience：
等待行为已登记。
上一行为：继续等待。
```

第二轮广播灯主反馈：

```text
doubt：
广播灯亮起。
没有广播，只有一段等待回答的空白。

control：
广播灯闪了两次。
系统正在校验你对目的地字段的修改。

obedience：
广播灯稳定亮着。
它像是在确认你仍然配合流程。
```

第三轮出口门主反馈：

```text
doubt：
出口门没有关闭。
屏幕显示：解释请求未完成。

control：
出口门打开一条缝。
屏幕显示：路径可修改，记录不可删除。

obedience：
出口门保持关闭。
屏幕显示：离站许可正在按流程生成。
```

时钟根据 anomaly 显示异常程度：

```text
anomaly 低：
23:47。秒针没有移动。

anomaly 中：
23:47 短暂跳到 23:46。

anomaly 高：
23:47 被重复刷新三次。
```

## 6.6 结局前行为摘要

第三轮结束、进入最终判断前，公告屏显示一段系统摘要。

不要直接显示数值：

```text
doubt = 3
control = 1
obedience = 0
```

应转成系统语言：

```text
解释请求：高
目的地干预：中
流程配合：低
叙事噪声：显著
最终判断生成中
```

## 6.7 不做内容

```text
不新增调查物；
不新增轮次；
不新增结局；
不让四个物件同时大幅变化；
不让调查物点击改变主状态；
不把 anomaly 做成第四路线。
```

## 6.8 验收标准

```text
玩家能感到每一轮至少一个车站元素发生明确变化；
不同倾向下主反馈物件文本不同；
时钟能表现 anomaly 程度；
第三轮后有行为摘要；
玩家不会因为四个物件同时变化而信息过载；
原有三结局判断不退化。
```

# 7. 需求 3：系统生成式入场与低保真几何车站背景

## 7.1 目标

把"三问校准完成 → 进入末班车站"从普通场景切换，升级为一次系统生成式入场。

玩家应感觉：

```text
车站不是自然出现的；
车站是叙事校准程序根据玩家选择生成出来的。
```

## 7.2 背景风格

使用：

```text
线条；
矩形；
圆圈；
几何轮廓；
低饱和色；
终端 / 系统生成感。
```

不使用：

```text
复杂插画；
写实车站背景；
大量 AI 图拼贴；
复杂 Shader；
大面积高饱和霓虹。
```

背景不是纯 ASCII 字母拼图，而是"终端感低保真几何背景"。

## 7.3 背景与按钮分离

重要边界：

```text
背景负责氛围；
按钮负责交互；
两者风格统一，但结构独立。
```

公告屏、时钟、广播灯、出口门不要嵌进背景里。

## 7.4 入场刷新方式

三问校准完成后：

```text
校准界面清空
→ 切入车站
→ 背景从上往下逐行 / 逐块显现
→ 设备按钮逐个显现
→ 主文本刷新出现
→ 显示系统待处理项：读取电子公告屏
```

动画时长建议：

```text
1.2～1.8 秒
```

必须支持跳过：

```text
点击任意处 / 按空格 → 立即完成入场动画
```

## 7.5 局部刷新方式

```text
车站背景：从上往下生成；
主文本：从左往右输出；
公告屏：从右往左或局部回刷；
最终判断：逐行打印。
```

## 7.6 不做内容

```text
不做不可跳过长动画；
不做复杂动态背景；
不做写实车站；
不做复杂角色；
不做 2D 移动；
不让背景抢走主文本和按钮。
```

## 7.7 验收标准

```text
三问结束进入车站时，有明显系统生成仪式感；
背景能传达低保真夜间车站氛围；
动画不会拖慢重玩；
动画可跳过；
背景不影响按钮可读性；
背景不与设备按钮点击区域混淆。
```

# 8. 需求 4：低保真设备按钮视觉化

## 8.1 目标

把公告屏、时钟、广播灯、出口门从普通文字按钮升级为可识别的低保真设备按钮，让玩家一眼知道它们是什么，同时保持清楚可点击。

## 8.2 布局

v0.2 第一版采用横向排列。

建议：

```text
[电子公告屏] [时钟] [广播灯] [出口门]
```

如果空间允许，公告屏可以稍宽，其余三个设备较窄。

不做复杂"车站控制面板"重排。

## 8.3 设备形状

时钟：

```text
方框数字时钟
显示 23:47
矩形边框
数字居中
偏等宽 / 数码感
```

广播灯：

```text
圆形灯点 + 标签
实际点击区域仍为矩形按钮
状态变化时亮灭或闪烁
颜色低饱和
```

电子公告屏：

```text
横向电子公告栏
多行信息
顶部小标题
与时钟区分明显
点击时可横向回刷
```

出口门：

```text
车站双开门
中间门缝
可带 EXIT / 出口 标识
状态变化时门缝可轻微亮起
```

## 8.4 实现方式

优先使用 Godot Control 节点：

```text
PanelContainer
MarginContainer
HBoxContainer
VBoxContainer
Label
Button
ColorRect
StyleBoxFlat
```

暂不引入复杂 PNG 图标或 AI 图素材。

设备按钮应支持：

```text
normal
hover
pressed
highlighted
inactive / disabled
```

## 8.5 不做内容

```text
不做写实图标；
不做复杂美术资源；
不与背景融合；
不牺牲可点击性；
不改变调查物点击逻辑；
不让调查物点击改变主状态数值。
```

## 8.6 验收标准

```text
玩家能一眼识别四个设备；
玩家知道四个设备可以点击；
横向排列不拥挤；
hover / pressed 有基本反馈；
设备图案不会抢主文本；
公告屏和时钟区分明显；
出口门能看出双开门意象。
```

# 9. 需求 5：系统锚点音效与低频环境音

## 9.1 目标

参考《小黑屋》用"火"建立极简 UI 的沉浸锚点，本项目用"公告屏刷新 / 系统运行声"建立末班车站的沉浸锚点。

目标不是加传统 BGM，而是让玩家感到：

```text
这个车站被系统维持着；
公告屏正在记录；
广播灯正在监听；
出口门有系统许可压力；
每次选择都有写入感。
```

## 9.2 音频总原则

不使用强旋律背景音乐。

优先使用：

```text
低频环境底噪；
短促系统提示音；
公告屏跳字声；
广播灯电流声；
出口门低频许可声。
```

声音要少而准。

## 9.3 核心声音锚点

v0.2 的核心声音锚点是：

```text
公告屏刷新声
```

它代表：

```text
系统正在记录；
系统正在回放；
系统正在写入；
系统正在判断。
```

它是本项目对应《小黑屋》"火声"的核心声音。

## 9.4 第一版必做声音

建议第一版只做 4 个声音：

```text
1. ambient_station_loop
   极低音量车站 / 电流 / 通风底噪，循环。
   
2. notice_refresh
   公告屏刷新 / 跳字声，用于公告屏点击、残影、最终判断生成。
   
3. choice_commit
   主线选择确认 / 记录写入声，用于 A/B/C/D 选择。
   
4. device_signal
   通用设备反馈声，先复用给广播灯、出口门、时钟。
```

后续再拆分：

```text
broadcast_electric
exit_gate_lock
clock_tick_back
ending_low_pulse
```

## 9.5 anomaly 与音效

v0.2 第一版可以先不做动态音频系统。

后续可扩展：

```text
anomaly 低：正常刷新声；
anomaly 中：刷新声略长；
anomaly 高：刷新声有短暂停顿 / 断裂 / 失真。
```

## 9.6 不做内容

```text
不做旋律型 BGM；
不做动态音乐系统；
不做语音播报；
不做大量不同音效；
不做恐怖惊吓音；
不使用未授权素材；
不让音效干扰阅读。
```

## 9.7 验收标准

```text
公告屏刷新声能成为玩家记忆点；
环境音低到不干扰阅读；
点击和选择有明确但克制的声音反馈；
广播灯 / 出口门等设备有基础信号声；
所有声音音量统一，不突兀；
关掉声音后，游戏仍可正常理解；
没有恐怖化、鬼怪化、廉价惊吓感。
```

# 10. 需求 6：AI 动态引导与受限选项改写

## 10.1 目标

建立 v0.2 的 AI 原生雏形。

目标不是做自由输入，也不是让 AI 生成完整剧情，而是让系统在特定时刻：

```text
读取玩家当前状态；
解释玩家刚才做了什么；
推测玩家行为意图；
给出冷淡的下一步提示；
在受限条件下改写一个选项显示文本。
```

玩家应感到：

```text
系统不只是显示预制文本；
它正在根据我的具体行为解释我；
它甚至会改写我可选择的行动。
```

## 10.2 v0.2 AI 定位

v0.2 的 AI 定位是：

```text
AI 原生体验雏形。
```

具体为：

```text
Mock AI 动态引导：必做候选；
受限选项改写：必做候选；
真实 API：可选实验开关，不作为默认必需。
```

## 10.3 AI 动态引导

AI 动态引导在玩家关键行为后触发，例如：

```text
点击公告屏后；
完成一轮主线选择后；
第三轮结束、最终判断前。
```

AI 读取：

```text
current_node_id；
current_phase；
choice_history；
last_choice_label；
clicked_interactables；
doubt；
control；
obedience；
anomaly；
dominant_trait；
initial_world_hint；
当前可用选项；
当前可用设备；
已触发 flags。
```

AI 输出 1～3 行系统解释文本。

文本应包含：

```text
玩家刚才做了什么；
系统如何归类该行为；
下一步建议或待处理项。
```

推荐系统口吻：

```text
上一行为已记录：读取电子公告屏。
系统推测：用户正在验证场景是否回应自身选择。
建议项：检查广播源 / 查看离站许可。
```

## 10.4 不直接写玩家心理

AI 不应直接说：

```text
你很害怕；
你很焦虑；
你其实想逃跑；
你内心不安。
```

应写成系统推测：

```text
系统推测：用户正在寻找规则边界。
系统判断：该行为更接近解释请求，而非离站尝试。
```

## 10.5 受限选项改写

在特定条件下，AI 可以改写 A/B/C/D 中一个选项的显示文本。

它改变的是：

```text
选项显示文本
```

不能改变：

```text
选项数量；
底层 intent；
state_delta；
next_node；
结局判断；
主线结构。
```

推荐触发条件：

```text
玩家已完成至少一轮主线；
玩家点击公告屏；
anomaly 达到阈值；
本局尚未触发过 AI 选项改写。
```

示例：

原选项：

```text
D. 不再回应，直接走向出口
```

AI 介入后刷新为：

```text
D. 执行系统建议：走向未标记出口
```

底层仍绑定：

```text
control + 1
doubt + 1
next_node = ""
```

## 10.6 API 接入策略

v0.2 默认不依赖真实 API。

建议：

```text
默认模式：Mock AI 动态引导 + Mock 选项改写；
实验模式：API 只生成动态引导文本；
选项改写逻辑仍由本地规则验证和绑定。
```

真实 API 不允许直接决定：

```text
state_delta；
next_node；
ending_id；
新增选项数量；
新增结局；
新增场景物件。
```

## 10.7 AI 等待与 fallback

AI 请求可能有 3～4 秒延时。

等待期间显示：

```text
系统正在解释上一行为……
公告屏正在回刷……
建议项生成中……
```

等待期间：

```text
禁用相关按钮；
显示生成中状态；
播放 notice_refresh 或轻微设备信号声；
4 秒未返回则使用 Mock fallback。
```

fallback 提示可写成世界内文本：

```text
系统解释超时。
使用本地判断结果。
```

## 10.8 v0.2 最小实验方案

推荐 v0.2 做一个最小实验：

```text
第二轮结束后，玩家点击公告屏；
如果 anomaly >= 2 且尚未触发过 AI 介入；
系统显示一段 AI / Mock AI 动态引导；
随后第三轮 D 选项刷新为"系统建议项"；
底层仍使用原本 D 选项的状态变化。
```

示例文本：

```text
电子公告屏刷新失败。
系统推测：用户正在寻找离开叙事的方法。
建议项已写入选项 D。
```

刷新后的选项：

```text
D. 执行系统建议：走向未标记出口
```

## 15. 最终结论

v0.2 需求已经足够充分，可以冻结。

v0.2 不应继续新增大需求。下一步应该进入分阶段实现。

v0.2 的三个最重要记忆点是：

```text
1. 车站从上往下被系统生成出来；
2. 玩家选择明显反馈到公告屏、广播灯、时钟、出口门；
3. 系统 / AI 在某一刻改写一个选项，让玩家意识到行动空间也被记录系统影响。
```

只要这三个点做清楚，v0.2 即使仍然是低保真，也有机会成为一个能让外部玩家感到惊艳的概念 Demo。
